# PRISMA ABYSS 10枠セーブ・既存バックアップ併存設計（実装前案）

作成日: 2026-08-04  
状態: **設計・監査のみ。ユーザー確認前のため未実装。**

## 1. 結論

現行の `App.save()` は同期的に `localStorage` へ保存し、呼出側はその場で `true / false` を受け取る設計である。
ルートJS/HTMLだけでも `App.save()` 呼出は234箇所あり、装備・通貨等の巻き戻し処理も同期的な保存結果を前提にしている。

そのため、全保存を一度に非同期IndexedDBへ置き換えることはしない。

推奨構成は次のとおり。

- **オートセーブ1枠**: 現行 `CONST.SAVE_KEY` / `localStorage` をそのまま正本として維持。
- **手動セーブ9枠**: IndexedDBへ、現在のオートセーブ内容のスナップショットを保存。
- **既存のデータ出力・データ読込**: `.rpgsave` の暗号化バックアップ／復元として残す。
- **外部ファイル・フォルダ連携**: 対応ブラウザだけで使える任意の追加機能。10枠セーブの前提にはしない。
- **IndexedDBが使えない場合**: 手動9枠だけを利用不可にし、現行のオートセーブ＋バックアップ／復元を継続。

この構成なら、戦闘結果ジャーナル、保存失敗時ロールバック、既存234箇所の保存呼出を壊さずに段階導入できる。

- `CONST.SAVE_KEY` 直接読込: 1箇所

直接アクセス箇所:

- `main.html` セーブ削除

### 容量上の注意

初期データは小さいが、実セーブには以下が増える。

- 装備・所持品・仲間・図鑑・進行フラグ
- 生成済み迷宮・戦闘再開情報
- 主人公および仲間のカスタム画像Data URL

特に512pxのWebP/JPEGカスタム画像を複数保存できるため、10枠全部を `localStorage` の複数キーへ複製する設計は避ける。

## 3. 「認証」と保存の関係

ブラウザ保存には、性質の違う3種類がある。

### 3.1 ブラウザ内セーブ（localStorage / IndexedDB）

- ゲームのサイト専用領域へ保存する。
- 通常はファイル選択や端末認証を要求しない。
- 10枠セーブのゲーム内UI、上書き、枠分け、オートセーブはこの領域だけで実現できる。
- 同じ端末でも、別ブラウザ、別ブラウザプロファイル、別URLでは別データになる。
- プライベートブラウズ、サイトデータ削除、保存禁止、容量不足では失われる／失敗する可能性がある。

### 3.2 永続ストレージ要求 (`navigator.storage.persist()`)

- ブラウザ内データが容量整理で自動削除されにくくなるよう要求する仕組み。
- フォルダアクセス権や端末の生体認証ではない。
- ブラウザが自動判断する場合があり、必ず許可されるものではない。
- 拒否・非対応でも、通常のブラウザ内保存は続けられる。

### 3.3 ユーザーが選んだ外部ファイル／フォルダへの直接書込

- File System Access API等を使う追加機能。
- ユーザー操作で保存先を選び、ブラウザの読書込許可を得る必要がある。
- 対応状況と許可の持続性がブラウザ・OSで異なる。
- Safari 26ではファイルへの直接書込機能が拡張されているが、ファイル／フォルダ選択、権限保持、ホーム画面Webアプリでの挙動はOS・ブラウザ差が残る。
- よって、外部書込は実行時の機能検出と実機試験を必須とし、権限を拒否された場合も10枠セーブを失わせない。

## 4. 推奨データ構造

### 4.1 オートセーブ

現行のまま:

```text
localStorage[CONST.SAVE_KEY] = 現在プレイ中の完全セーブJSON
```

これは「オート1枠」であり、戦闘・移動・イベント等の既存 `App.save()` が更新する。

### 4.2 手動9枠

IndexedDB:

```js
DB: PRISMA_ABYSS_SAVE_SLOTS
version: 1

objectStore: slots
keyPath: slotId

{
  slotId: 1, // 1〜9
  schemaVersion: 1,
  updatedAt: "2026-08-04T...Z",
  metadata: {
    heroName,
    heroLevel,
    playTimeMs,
    locationLabel,
    storyStep,
    abyssMaxFloor,
    saveVersion,
    payloadBytes
  },
  payload: "{...完全セーブJSON...}",
  checksum: "..."
}
```

手動保存は、現在の `App.data` を `App.serializeSaveData()` で確定し、対象枠へ1トランザクションで上書きする。

### 4.3 アクティブ情報

```js
{
  lastLoadedSource: "auto" | 1 | 2 | ... | 9,
  lastManualSlot: 1 | ... | 9 | null
}
```

これはセーブ本体と分ける。手動枠をロードした後も、通常プレイ中はオート枠だけが更新される。

## 5. 画面と操作案

### タイトル

- `つづきから`: オート枠を開く。
- `セーブデータ`: オート1枠＋手動9枠一覧を開く。
- 手動枠の操作: `ロード`、`削除`、`バックアップ出力`。
- 空枠は空欄表示。

### ゲーム内

- `セーブ`: 手動1〜9を選択。
- 既存枠は上書き確認。
- オート枠は手動上書き不可。
- 保存成功後も現在のプレイはオート枠で継続。

### 新規ゲーム

推奨は、新規ゲーム開始時にオート枠を作り、必要な時点で手動枠へ保存する方式。
複数周回を明確に分ける運用を望む場合は、開始前に手動枠を選ばせる別案もある。

## 6. ロード時の安全手順

手動枠ロード:

1. IndexedDBから枠を読み出す。
2. JSON解析、最低限の形式検証、チェックサム確認。
3. `migrateImportedSaveData()` 相当の互換処理を通す。
4. 現在のオート枠を一時退避。
5. 読み出した内容を `CONST.SAVE_KEY` へ同期書込。
6. 書込内容を再読込・再解析して確認。
7. 成功後にページをリロード。
8. 失敗時は退避したオート枠へ戻す。

手動枠を直接 `App.data` へ代入して続行せず、必ず現行起動経路から再読込する。

## 7. 既存バックアップ／復元との併存

既存機能は削除しない。

### 現状維持

- `データ出力`: 現在のオート枠を暗号化 `.rpgsave` として出力。
- `データ読込`: ファイル内容を確認し、オート枠へ復元。
- 旧JSON形式の読込互換も維持。

### 10枠対応後の追加案

- 手動枠ごとの `.rpgsave` 出力。
- 読込先を「オートへ復元」または「手動1〜9へ格納」から選択。
- 全10枠一括バックアップは別形式・別バージョンで後から追加。

最初から全枠バックアップまで同時実装せず、個別枠が安定してから追加する。

## 8. 外部ファイル連携案

機能名案: `外部バックアップ先を連携`

### 対応環境

- 対応ブラウザでは、ユーザーが選んだファイルまたはフォルダへのアクセス許可を得る。
- 許可済みハンドルをIndexedDBへ保存できる環境では再利用する。
- 権限が切れていれば、再許可を求める。

### 動作

- 連携成功時だけ、手動保存後または指定した安全なオートセーブ時に外部バックアップを書き出す。
- 外部書込失敗はゲーム内セーブ成功を取り消さない。
- 「ゲーム内保存成功／外部バックアップ失敗」を別々に表示する。
- 未対応、拒否、取消の場合は、既存のダウンロード方式を案内する。

### 非採用事項

- 外部フォルダ権限を10枠セーブの必須条件にしない。
- 外部書込失敗時に単一セーブへ切り替える設計にしない。
- iOS Safariで同じフォルダへ無確認で継続書込できると案内しない。

## 9. PC・スマートフォン差

### PC Chromium系

- IndexedDBによる10枠: 利用可能。
- ファイル／フォルダ連携: 比較的実装しやすい。
- インストール済みPWAでは権限が持続する場合がある。

### Android Chromium系

- IndexedDBによる10枠: 利用可能。
- ファイルアクセスAPIは環境差があるため、機能検出して提供。
- 画面復帰・省メモリ終了を考慮し、保存完了表示前にトランザクション完了を待つ。

### iPhone/iPad Safari・ホーム画面Webアプリ

- IndexedDBによる10枠: 利用可能。
- `navigator.storage.persist()` はホーム画面Webアプリ等の条件で許可されやすくなる可能性がある。
- 外部ファイルへの直接書込は、Safariのバージョンと実行形態を機能検出し、実機で確認できた場合だけ表示する。
- フォルダ選択と権限保持を全端末共通とは扱わず、既存のファイル出力／読込を外部バックアップの基本手段として残す。

### プライベートブラウズ／保存禁止

- IndexedDBや他のブラウザ保存が利用不可・一時的になる可能性がある。
- 起動時に保存可否を診断し、手動9枠を無効化。
- 現行 `localStorage` も失敗する場合は、プレイ継続前に警告する。

## 10. 実装段階

### Phase S1: 保存能力診断と設計確定

- IndexedDB開閉試験。
- `navigator.storage.estimate()` 表示用診断。
- `navigator.storage.persisted()` 状態確認。
- 現行セーブ実サイズ測定UI／開発ログ。
- ユーザー回答を設計へ反映。

### Phase S2: 手動9枠ストレージ層

- `save_slots.js` 新設。
- 保存、読込、削除、一覧、チェックサム。
- 旧オート枠は変更しない。
- Node試験＋ブラウザIndexedDB試験。

### Phase S3: タイトル・ゲーム内UI

- 枠一覧、メタデータ、上書き確認。
- ロード時の退避・復元。
- タイトルの削除処理を枠対応。

### Phase S4: バックアップ連携

- 現行出力／読込を枠選択対応。
- 対応環境のみ外部バックアップ先連携。
- 未対応／拒否時の既存方式フォールバック。

## 11. 実装前にユーザーへ確認する事項

1. `つづきから` は常に最新オート枠を開くか、枠一覧を開くか。
2. 手動枠ロード後、オート枠をそのデータで更新してよいか。
3. 新規ゲーム開始時に手動枠を先に選ばせるか、オート枠だけで開始するか。
4. バックアップ読込は、オート枠への復元を既定にするか、読込先枠を毎回選ばせるか。
5. 外部バックアップ先連携は、初回10枠実装と同時に入れるか、10枠安定後の追加にするか。
6. 手動枠ごとの名前変更（例: 「本編」「周回用」）を初回から必要とするか。

## 12. 現時点の推奨回答

- `つづきから`: オート枠を開く。
- 手動枠ロード: オート枠へ安全にコピーしてから開始。
- 新規ゲーム: オート枠で開始。最初の手動保存時に枠を選ぶ。
- バックアップ読込: 読込先を毎回選択。ただし既定カーソルはオート枠。
- 外部連携: 10枠安定後に追加。
- 枠名: 初回は不要。主人公名・Lv・場所・日時を自動表示。
