## 整理方針

削除対象は、実行時参照がなく、現行仕様の正本でもなく、公開Gitまたはユーザー保有バックアップから復元できるものに限定する。

保持対象:

- 実行時に読み込むJS、HTML、CSS、Service Worker、manifest
- `assets.js`、`monsters.js`、map library manifestから参照される画像
- シナリオ正本、story bible、設計仕様、現在の製品指示
- セーブ移行、イベント復旧、派生状態再構築など、既存セーブの安全に関わる処理
- Phaser失敗時の旧Canvas安全フォールバック（削除判断待ち）

第一段階の削除対象:

- `work/` の画像生成・動画抽出・一時集計物
- `archive/` の差替え手順、handoff、完了済みPhase記録、旧QA画像、旧画像退避
- `logs/` の過去実行ログと古い資産監査出力（管理説明は保持）

## 検証基準

変更前の `node tools/validation/run-all.js` は59本中28本が失敗した。失敗には次の三種類が混在する。

1. 現行実装の名称・コード文字列・旧画像命名を前提にした脆い検証
2. VMスタブやfixtureが現行APIへ追随していない検証
3. 実際の仕様不整合または回帰の可能性があり、個別確認が必要な指摘

したがって、一括検証を通すために実装を旧形へ戻したり、失敗検証を一律削除したりしない。構文、起動、セーブ、Service Worker、全量キャッシュ、Phaser表示を中核ゲートとし、領域別検証は仕様との一致を確認してから修正または廃止する。

## 削除してはいけない互換処理

名称に `legacy`、`fallback`、`migration` が含まれるだけでは削除根拠にならない。画像読み込み失敗時の代替、ランダム生成失敗時の安全マップ、イベント中断復旧、破損セーブ修復、派生フラグ再構築は恒常的な防御処理であり、短期移行とは別扱いにする。

## Phaser障害時試験

比較用一時クローンでPhaserスクリプトだけを意図的に読込不能にし、PCと390×844のスマートフォン幅で完全新規開始を実行した。

- Phaser canvasは生成されず、旧Canvasが `opacity: 1` で表示された。
- タイトル、新規作成、キャッシュ選択、リュミナ村開始、会話、画面内操作UIまで到達した。
- スマートフォン幅で横あふれは発生しなかった。

この結果、旧Canvasは作業残骸ではなく、現在も動作する障害時機能であると確認できた。「現在の機能を壊さない」を優先する限り、現時点での削除は行わない。

通常時の追加負荷は、320×320×4 byte換算で約0.39MiBのCanvas画素バッファと、`main.js` 内に含まれる旧描画コードの配信分である。旧Canvas専用の画像再取得や毎フレームの旧描画はない。対してPhaser本体は約1.14MiBで、旧Canvasを削除してもこれは減らない。安全フォールバックの価値に比べ、現時点の削減効果は小さいと判断する。
